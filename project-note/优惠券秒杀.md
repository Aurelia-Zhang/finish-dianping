# 优惠券秒杀

## 1. Redis 唯一 ID 生成器

### 1.1 核心代码解析

在 `RedisIdWorker.java` 的核心实现中：

```java
// 核心逻辑片段
public long nextId(String keyPrefix) {
    // 1. 生成时间戳
    LocalDateTime now = LocalDateTime.now();
    long nowSecond = now.toEpochSecond(ZoneOffset.UTC);
    long timestamp = nowSecond - BEGIN_TIMESTAMP;

    // 2. 生成序列号
    // 获取当前日期，用于 Redis 的 key
    String date = now.format(DateTimeFormatter.ofPattern("yyyy:MM:dd"));
    // 自增
    long count = stringRedisTemplate.opsForValue().increment("icr:" + keyPrefix + ":" + date);

    // 3. 拼接并返回
    return timestamp << COUNT_BITS | count;
}
```

---

### 1.2 为什么时间戳是“减出来的”？

代码中 `long timestamp = nowSecond - BEGIN_TIMESTAMP;` 这一步叫做**偏移量计算**。

*   **节省空间**：Java 的 `long` 是 64 位。如果我们直接用“从 1970 年至今的秒数”（约 17 亿），它占用的比特位较多。
*   **延长使用寿命**：通过设置一个 `BEGIN_TIMESTAMP`（项目开始的时间，比如 2022 年 1 月 1 日），我们只计算**从那一天起到现在的差值**。
*   **结构分配**：这个 ID 的 64 位被拆分成了：
    *   **符号位**：1 位（始终为 0）。
    *   **时间戳**：31 位（大约可以用 69 年）。
    *   **序列号**：32 位（每秒支持约 42 亿个自增 ID）。

**结论**：减法是为了让“时间戳”这一部分从 0 开始计数，充分利用 31 位空间。

---

### 1.3 自增（序列号）具体是怎么回事？

这里利用了 **Redis 的原子性自增命令 `INCR`**：

1.  **Key 的设计**：`icr:order:2026:02:19`。
    *   注意：Key 里面带了**日期**。这意味着**每天**的序列号都是从 1 开始重新计数的。
2.  **为什么要带日期？**
    *   如果全局只有一个 Key，几年后 `long` 类型的序列号可能会溢出。
    *   方便统计：你可以轻松通过 Redis 看到每一天产生了多少订单。
3.  **自增逻辑**：
    *   第一个用户下单：Redis 执行 `INCR`，返回 1。
    *   第二个用户下单：Redis 执行 `INCR`，返回 2。
    *   以此类推……

### 1.4 模拟 ID 生成过程

假设我们的 `COUNT_BITS` 是 32（即给序列号预留 32 位）。

**场景：2026 年 2 月 19 日，某秒内的第 5 个订单。**

#### 第一步：计算时间戳 (timestamp)
*   当前秒数：`1740000000` (假设)
*   初始秒数 `BEGIN_TIMESTAMP`：`1640995200` (2022年)
*   `timestamp = 1740000000 - 1640995200 = 99004800`
*   二进制表示（假设简化）：`10111100...` (共 31 位)

#### 第二步：获取序列号 (count)
*   Redis 执行 `increment("icr:order:2026:02:19")`
*   返回 `count = 5`
*   二进制表示：`00000000...00000101` (共 32 位)

#### 第三步：二进制拼接 (移位与或运算)
1.  **左移**：`timestamp << 32`
    *   把时间戳向左移动 32 位，空出右边的 32 位。
    *   结果：`[31位时间戳] [32个0]`
2.  **或运算**：`| count`
    *   把刚才的 5 填进那 32 个 0 的位置。
    *   结果：`[31位时间戳] [000...0101]`

**最终结果**：得到一个唯一的 64 位长整型数字。这个 ID 的本质是一个 **64 位的组合体**。高位代表时间，保证了 ID 的**趋势递增**（时间总是在往前走）；低位代表每秒内的计数，保证了**同一秒内 ID 的唯一性**。

### 1.5 常见疑惑解答 (Q&A)

#### Q: Redis 的 Key 和最终生成的 ID 是什么关系？
**A:** Key 是“计数器”，ID 是“最终产品”。
*   **Key** 是 Redis 里的一个变量（如 `icr:order:2026:02:19`），它的值（Value）只是一个自增的数字（如 `5`）。
*   **ID** 是 Java 代码最终生成的 64 位长数字。它由“时间戳”和“Redis 的 Value”拼接而成。你可以把 Value 看作是生成 ID 的**原材料**。

#### Q: Redis 里面存的到底是什么？是 Key-Value 对吗？
**A:** 是的。在 Redis 层面就是简单的键值对：
*   **Key**: `icr:order:2026:02:19`
*   **Value**: `5` (这个数字会随着调用 `increment` 而不断增加)

#### Q: Java 的 `increment` 方法对应 Redis 什么命令？怎么手动执行？
**A:** 对应 Redis 的 **`INCR`** 命令。
在 Redis 客户端中输入：
```bash
INCR icr:order:2026:02:19
```
执行后，Redis 会自动将该 Key 的值加 1 并返回加完后的结果。

#### Q: 单元测试 `testIdWorker` 具体是在测什么？
**A:** 这是一个**多线程压力测试**。
1.  **模拟高并发**：利用 `CountDownLatch` 和 `线程池` 同时开启 300 个线程。
2.  **模拟任务**：每个线程疯狂生成 100 个 ID。
3.  **目的**：
    *   验证**安全性**：3 万个 ID 同时生成，会不会出现重复？
    *   验证**性能**：生成 3 万个 ID 总共耗时多久？

## 2. 乐观锁解决超卖问题

### 2.1 为什么需要乐观锁？
在秒杀场景下，如果 100 个线程同时查询库存，发现库存都剩 1 个，然后大家一起去扣减，如果不加控制，库存会变成 -99，这就是**超卖**。

### 2.2 方案一：传统的 CAS (完全相等)
**核心思想**：扣减库存时，判断库存是否还是我刚才查到的那个值。
```java
.eq("stock", voucher.getStock()) // where stock = ?
```
*   **缺点**：成功率极低。如果 100 个人同时看到库存是 100，第 1 个人扣减成功后库存变 99，剩下的 99 个人发现库存不再是 100 了，全都扣减失败。明明还有 99 个货，却卖不出去。

### 2.3 方案二：改进的 CAS (大于 0 即可)
**核心思想**：只要库存大于 0，就允许扣减。
```java
.gt("stock", 0) // where stock > 0
```
*   **优点**：大幅提升并发成功率。只要有货，大家排队（通过数据库行锁）一个个扣减即可，不会因为库存数字变了就导致“误判”失败。

### 2.4 知识扩展：LongAdder
在高并发计数时，`AtomicLong` 的底层 CAS 自旋会导致 CPU 压力过大。
*   **LongAdder 原理**：将一个数字拆分成多个“格子”（Cells）。不同线程去加不同的格子，最后求和。
*   **类比**：一个售票窗口排队太长，我就多开几个窗口同时卖票，最后把每个窗口卖出的票数加起来。

## 3. 一人一单与事务/代理问题

### 3.1 核心需求
为了防止同一个用户通过并发请求多次领券，必须在创建订单前判断该用户是否已经拥有该优惠券。

### 3.2 锁的粒度优化
*   **方案**：使用 `synchronized(userId.toString().intern())`。
*   **原理**：
    *   不锁整个方法：避免所有用户都排队，提升并发性能。
    *   `.intern()`：确保同一个用户 ID 对应的字符串对象在常量池中是唯一的，从而保证同一个用户的所有请求都能被同一把锁拦住。

### 3.3 锁与事务的先后顺序（锁失效问题）
*   **问题**：如果锁在事务方法内部，会导致“锁释放了但事务还没提交”。
*   **现象**：线程 A 释放锁的一瞬间，线程 B 进来，此时 A 的订单还没写入数据库（事务未提交），B 查到的 count 依然是 0，导致重复下单。
*   **对策**：必须在调用事务方法**之前**加锁，确保事务提交后才释放锁。

### 3.4 Spring 事务失效问题（代理模式）
*   **现象**：在类内部直接调用带有 `@Transactional` 的方法（如 `this.createVoucherOrder()`），事务不会生效。
*   **原因**：Spring 事务是基于 AOP 代理实现的。内部调用是直接通过 `this` 对象调用，绕过了 Spring 产生的代理对象，导致 AOP 切面（开启/提交事务的代码）无法执行。
*   **解决方案**：
    1.  引入 `aspectjweaver` 依赖。
    2.  启动类开启 `@EnableAspectJAutoProxy(exposeProxy = true)`。
    3.  通过 `AopContext.currentProxy()` 获取当前的代理对象进行调用。

```java
// 正确调用示例
synchronized(userId.toString().intern()) {
    // 获取代理对象（只有代理对象调用方法，事务才会生效）
    IVoucherOrderService proxy = (IVoucherOrderService) AopContext.currentProxy();
    return proxy.createVoucherOrder(voucherId);
}
```
